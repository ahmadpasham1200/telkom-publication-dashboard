================================================================
1. APA YANG DIHASILKAN SATU KALI SCRAPING?
================================================================
Satu panggilan scrape_scholar() menghasilkan SATU "envelope"
(dict JSON). Envelope ini disimpan utuh apa adanya, sukses
maupun gagal.

Struktur envelope (level atas):
  - run_id            : UUID unik per run
  - source            : sumber data
  - started_at        : waktu mulai scraping
  - finished_at       : waktu selesai scraping
  - status            : SUCCESS / BLOCKED / TIMEOUT /
                        NO_DATA / PARSING_ERROR
  - records_fetched   : jumlah baris publikasi berhasil diambil
  - records_failed    : jumlah baris yang gagal diambil
  - error_message     : pesan error (None kalau sukses)
  - data              : isi utama (lihat di bawah)

Isi "data":
  - scholar_id        : ID profil Google Scholar
  - name              : nama peneliti
  - h_index           : h-index dari profil
  - rows              : daftar publikasi (1 elemen = 1 publikasi)
  - failures          : daftar kegagalan per baris
  - domain            : domain yang dipakai saat scraping
  - batches           : jumlah batch
  - elapsed           : durasi scraping (detik)

Setiap elemen "rows" (satu publikasi) punya field:

  Dari halaman DAFTAR (list page):
    - title            : judul publikasi
    - authors          : penulis BENTUK PENDEK (terpotong "...")
    - venue            : jurnal/konferensi
    - extra            : info tambahan mentah
    - citations        : jumlah sitasi
    - year             : tahun (mentah)
    - publication_year : tahun (sudah dibersihkan)
    - detail_url       : tautan ke halaman detail

  Dari halaman DETAIL (detail page, diambil per publikasi):
    - detail_title       : judul versi detail
    - detail_authors     : penulis LENGKAP
    - detail_date        : tanggal terbit
    - detail_venue       : jurnal/konferensi versi detail
    - detail_venue_label : label venue (jurnal/konferensi)
    - detail_volume      : jilid
    - detail_issue       : terbitan
    - detail_pages       : halaman
    - detail_publisher   : penerbit
    - detail_description : deskripsi/abstrak
    - detail_citations   : sitasi versi detail
    - detail_link        : tautan artikel
    - detail_pdf_link    : tautan PDF


================================================================
2. DATA MASUK KE TABEL MANA?
================================================================
Alur: raw -> core (lewat mapper to_core_rows). Staging BUKAN
tahap antara: staging ditulis PARALEL dalam transaksi yang sama
sebagai salinan audit nilai yang sudah dibersihkan, dan tidak
pernah dibaca kembali oleh loader (tidak ada SELECT dari staging
di src/).

--- LAYER RAW (data mentah apa adanya) -------------------------
  raw.scholar_scrape_result
    1 baris = 1 envelope utuh (JSONB di kolom raw_envelope).
    Run yang GAGAL pun tetap disimpan di sini, supaya bisa
    ditelusuri kenapa scraping bermasalah.
    Kolom: result_id, scholar_id, scraped_at, run_id, status,
           raw_envelope.

  raw.scholar_author
    1 baris per run per profil.
    Kolom: result_id, urutan (=0), scholar_id, nama, h_index,
           domain, batches, elapsed.

  raw.scholar_publication
    1 baris per publikasi per run. Semua field mentah disimpan
    sebagai TEXT, termasuk field detail_*.

--- LAYER STAGING (salinan audit paralel, bukan tahap antara) ---
  staging.stg_authors
    Profil peneliti hasil bersih (stg_author_id, result_id,
    urutan, scholar_id, nama, h_index, domain, batches, elapsed).

  staging.stg_publications
    Publikasi hasil bersih, termasuk kolom revisi seperti
    publication_year.

--- LAYER CORE (tabel final untuk dashboard) -------------------
  core.authors
  core.publications
  core.publication_authors   (relasi publikasi-penulis,
                              ada kolom author_order)
  core.author_metrics
  core.publication_metrics

Catatan:
  - Penulisan staging + core terjadi dalam SATU transaksi.
  - Blok staging hanya berjalan kalau parameter profil tidak None.
  - Natural key untuk upsert: (title, publication_year) di
    core.publications (sejak migrasi 06; migrasi itu mengganti
    kunci lama (title, publication_date) dari 03) dan
    lower(btrim(name)) di core.authors, jadi run ulang tidak
    menduplikasi data.


================================================================
3. APAKAH SEMUA DATA GOOGLE SCHOLAR KEBACA?
================================================================
Jawaban singkat: YA, semua field yang tersedia di halaman
Google Scholar yang di-scrape ikut tersimpan di layer raw.
Tidak ada data yang "hilang". Yang membedakan hanyalah
seberapa lengkap field-nya, dan itu tercatat apa adanya.

Penjelasan:

  - Halaman DAFTAR (list page) hanya menampilkan versi pendek:
    nama penulis terpotong ("..."), tanpa tanggal terbit
    lengkap, tanpa volume/issue/halaman/penerbit.

  - Halaman DETAIL (detail page) berisi versi lengkap: semua
    penulis, tanggal terbit, jurnal/konferensi, jilid, terbitan,
    halaman, penerbit, deskripsi, dan tautan. Scraper mengunjungi
    halaman detail untuk SETIAP publikasi.

  - Kalau halaman detail gagal diambil -> field detail_* bernilai
    None, tapi baris publikasinya tetap tersimpan.

  - Field yang tidak ada / label tidak dikenal di halaman detail
    -> None (tidak error, tidak mematikan run).

  - Run yang gagal total (BLOCKED / TIMEOUT / NO_DATA /
    PARSING_ERROR) tetap tersimpan di raw.scholar_scrape_result.

  - Konsekuensi yang terlihat di data core: jumlah baris
    publication_authors berubah 50 -> 45. Penyebabnya adalah
    kebijakan "3j" (jurnal/jurnal/jurnal) plus fakta bahwa
    publikasi yang sumbernya halaman detail ditulis ulang
    berdasarkan daftar penulis LENGKAP dari halaman detail
    (33 penulis dihapus, 28 ditambahkan, net -5). Detail
    lengkapnya ada di STATUS_KERJA.txt bagian hasil perbaikan 3.
