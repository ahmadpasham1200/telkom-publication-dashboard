1. RINGKASAN KEPUTUSAN YANG SUDAH DISETUJUI PENGGUNA
--------------------------------------------------------------------------------

Kesepakatan pengguna (dari instruksi P56, dianggap FINAL):

  K1. Lingkup tetap RAW-only: scraping Google Scholar -> database RAW ->
      berhenti. Tanpa backfill, cleaning, enrichment, staging, atau
      pemuatan CORE.
  K2. Nama penulis dipertahankan persis sesuai teks dan urutan dari
      Google Scholar.
  K3. Setiap penulis disimpan sebagai entri individual terhubung ke
      publikasi.
  K4. `author_order` menyimpan urutan penulis dari Google Scholar
      (0-based mengikuti urutan tampil; P54 §2.4).
  K5. `author_role` memisahkan peran HANYA berdasarkan urutan:
      - `penulis_pertama`  = penulis pada urutan pertama (author_order=0)
      - `co_author`        = penulis pada urutan berikutnya (author_order>0)
  K6. Status pemilik profil disimpan di kolom TERPISAH
      `profile_owner_status`, kandidat nilai:
      - `pemilik_profil`
      - `bukan_pemilik_profil`
      - `belum_terverifikasi`
  K7. Pemilik profil ditentukan dari IDENTITAS profil Google Scholar yang
      sedang di-scrape, BUKAN dari urutan. Orang yang sama bisa berstatus
      `co_author` (role) sekaligus `pemilik_profil` (status) pada publikasi
      yang sama — kedua kolom independen.
  K8. `pemilik_profil` TIDAK boleh ditetapkan hanya dari kemiripan nama.
      Identitas belum terverifikasi -> `belum_terverifikasi`.
  K9. Jangan menganggap pemilik profil selalu penulis pertama (didukung
      fixture P54-A: posisi 2, 3, dan 6).
  K10. `data dosen/Data dosen.xlsx` boleh jadi referensi identitas; nama
      sumber Google Scholar TIDAK BOLEH diganti nama Excel.
  K11. Kolom RAW lama dipertahankan; tanpa backfill.
  K12. HTTP 429 BUKAN bukti nama penulis tidak ada; tanpa teknik
      penghindaran pembatasan Scholar.

Implikasi terbesar terhadap P55: desain P55 menggabungkan peran dalam satu
kolom `peran` ('pemilik'|'co_author'|'belum_terverifikasi'). Kesepakatan
baru MEMISAHKAN dua dimensi:
  - `author_role`  = fungsi murni dari author_order (selalu bisa diisi,
                     tidak tergantung verifikasi apa pun),
  - `profile_owner_status` = hasil verifikasi identitas pemilik profil.
Ini menghapus ambiguitas P55 (peran 'belum_terverifikasi') dan menyelesaikan
pertanyaan lama P54 Q1 ("penulis utama" = penulis pertama ATAU pemilik
profil? Jawaban: keduanya dimensi berbeda, disimpan di kolom terpisah).

4. ANALISIS: `belum_terverifikasi` — NILAI `profile_owner_status` ATAU
   KOLOM STATUS IDENTITAS TERPISAH? (tugas #6)
--------------------------------------------------------------------------------

Opsi A (kandidat pengguna, K6): `belum_terverifikasi` sebagai NILAI ketiga
  `profile_owner_status`.
  Konsekuensi:
  + Satu kolom, satu sumber kebenaran, tanpa NULL (NOT NULL dengan tiga
    nilai eksplisit).
  + Query sederhana: WHERE profile_owner_status = 'pemilik_profil'.
  + Makna harfiah tepat: "status pemilik belum dapat ditetapkan" — karena
    identitas belum terbukti, BAİK kemungkinan pemilik MAUPUN kemungkinan
    bukan-pemilik tidak boleh diklaim (K8). Jika identitas terverifikasi
    tetapi nama pemilik tidak ditemukan di daftar, status yang benar justru
    'bukan_pemilik_profil' (bukti ketiadaan setelah verifikasi) — kasus ini
    tetap terwakili.
  − Ketika verifikasi gagal, seluruh baris publikasi menjadi
    'belum_terverifikasi' — tidak ada pemisahan "kemungkinan besar bukan
    pemilik". Ini disengaja: tanpa bukti, tanpa klaim.

Opsi B: kolom terpisah `verifikasi_identitas` ('terverifikasi' |
  'belum_terverifikasi') + `profile_owner_status` hanya ('pemilik_profil' |
  'bukan_pemilik_profil', boleh NULL saat gagal verifikasi).
  Konsekuensi:
  + Memisahkan dimensi teknis (bukti verifikasi) dari dimensi bisnis
    (kepemilikan).
  − Membutuhkan NULL pada profile_owner_status (melanggar kesederhanaan
    NOT NULL) ATAU nilai ketiga terselip juga di sana -> redundansi.
  − Konsistensi antar-dua-kolom harus dijaga di banyak titik (gampang
    bocor: verifikasi='belum' tetapi status='pemilik').
  − Dua kolom untuk satu pertanyaan tunggal "apakah ini pemilik profil?".

Rekomendasi (BUKAN persetujuan): Opsi A — `belum_terverifikasi` tetap sebagai
nilai `profile_owner_status`, tanpa kolom verifikasi terpisah. Alasan utama:
domain ketiga nilai sudah tertutup penuh (pemilik / bukan pemilik / tidak
bisa diputuskan), kegagalan verifikasi adalah SATU-satunya alasan status
tidak bisa diputuskan (K8), dan desain tanpa NULL paling konsisten dengan
gaya skema repo. Konsekuensi yang diterima: ketika referensi identitas
tidak tersedia (file hilang/ambigu/nama tak cocok), seluruh baris publikasi
menghasilkan 'belum_terverifikasi' — konservatif, sesuai K8/K10, dan
dapat diperbarui pada run berikutnya bila referensi sudah benar (append-per-
run di RAW, tanpa backfill).
Status: rekomendasi BELUM disetujui sebagai bentuk final — dikunci bersama
persetujuan skema di Tahap 0/1. Catatan: kandidat nilai di K6 sudah sama
dengan Opsi A, sehingga rekomendasi ini menyelaraskan, bukan menentang,
kesepakatan pengguna.

5. RANCANGAN KOLOM TABEL AUTHOR RAW (FINAL — menggabungkan P55 + K1..K12)
--------------------------------------------------------------------------------

  raw.scholar_publication_author (
      raw_publication_author_id  SERIAL       PRIMARY KEY,
      raw_publication_id         INTEGER      NOT NULL
                                  REFERENCES raw.scholar_publication(
                                      raw_publication_id),
      author_order               INTEGER      NOT NULL,
      author_name                TEXT         NOT NULL,
      author_role                TEXT         NOT NULL,
      profile_owner_status       TEXT         NOT NULL,
      scholar_id                 VARCHAR(50),
      sumber                     TEXT         NOT NULL,
      daftar_terpotong           BOOLEAN      NOT NULL DEFAULT FALSE,
      created_at                 TIMESTAMP    NOT NULL DEFAULT now(),
      CONSTRAINT uq_raw_scholar_publication_author_pub_urutan
          UNIQUE (raw_publication_id, author_order)
  );

Penjelasan (tipe | nullable | alasan):
- raw_publication_author_id — SERIAL | NOT NULL | PK surrogate, ikut pola
  raw (04:38/:78).
- raw_publication_id — INTEGER | NOT NULL | FK -> raw.scholar_publication
  (raw_publication_id); TERVERIFIKASI PK target (04:78). result_id bukan PK
  publikasi (04:81/:134) sehingga tidak dipakai sebagai FK relasi ini.
- author_order — INTEGER | NOT NULL | urutan tampil Scholar 0-based (K4).
  Bagian UNIQUE gabungan; tidak diurutkan ulang loader.
- author_name — TEXT | NOT NULL | teks PENULIS PERSIS dari sumber
  (_pecah_penulis: strip per bagian + buang elipsis; tanpa pembalikan/kapital
  ulang/pengayaan — K2). Kandidat nama fisik; alternatif `nama` (gaya raw
  lama) diputuskan di gerbang skema.
- author_role — TEXT | NOT NULL | 'penulis_pertama' | 'co_author' (K5;
  rule di §3, invarian I1).
- profile_owner_status — TEXT | NOT NULL | 'pemilik_profil' |
  'bukan_pemilik_profil' | 'belum_terverifikasi' (K6; aturan di §6).
- scholar_id — VARCHAR(50) | nullable | hanya baris pemilik terverifikasi
  (D-3); co-author NULL permanen di lingkup ini.
- sumber — TEXT | NOT NULL | 'detail' | 'daftar' (D-1).
- daftar_terpotong — BOOLEAN | NOT NULL | DEFAULT FALSE (D-1); TRUE hanya
  bila sumber='daftar' dan string asli memuat elipsis.
- created_at — TIMESTAMP | NOT NULL | DEFAULT now() (konvensi 03:50).

Constraint & deduplikasi:
- UNIQUE (raw_publication_id, author_order) — satu penulis per posisi per
  publikasi; ON CONFLICT DO NOTHING + fallback SELECT saat retry (RETURNING
  kosong pada konflik — pola terverifikasi postgres.py:1423-1425, ditulis
  ulang di P55 §3). Idempoten untuk retry run sama; append-per-run untuk
  run berbeda (konsisten raw.scholar_publication).
- TANPA unique nama (identitas orang tidak disamakan berdasarkan nama —
  P54 §4, K10).
- Tanpa CHECK constraint (ikuti gaya raw yang ada); validasi nilai di kode +
  tes.
- Kolom lama authors/detail_authors TETAP (K11); tanpa backfill: baris relasi
  hanya untuk run baru (K1).

6. ATURAN PENETAPAN STATUS & PENANGANAN KASUS KHUSUS
--------------------------------------------------------------------------------

Aturan `profile_owner_status` (per baris author, per run):
  P1. Verifikasi LOLOS (nama profil #gsc_prf_in terdaftar di referensi
      Excel dengan scholar_id yang sama persis dengan run — kecocokan eksak
      setelah normalisasi spasi + casefold; tanpa fuzzy) DAN posisi ini
      cocok rantai kecocokan (eksak casefold -> _bentuk_pendek ->
      _varian_nama_pemilik[husus sumber detail], postgres.py:591-741):
      baris ini 'pemilik_profil' + scholar_id=ID run. Baris lain pada
      publikasi yang sama: 'bukan_pemilik_profil'.
  P2. Verifikasi LOLOS tetapi TIDAK ADA posisi yang cocok (nama pemilik
      tidak muncul di daftar publikasi ini): semua baris
      'bukan_pemilik_profil'; statistik `pemilik_tidak_ditemukan`.
  P3. Verifikasi GAGAL (tidak ada di Excel / ambigu / scholar_id berbeda /
      Excel tidak ada atau tidak terbaca): TIDAK ADA 'pemilik_profil';
      posisi yang cocok rantai kecocokan -> 'belum_terverifikasi'
      (kandidat, tidak diklaim — K8); baris lain -> 'belum_terverifikasi'
      juga (tanpa verifikasi, "bukan pemilik" pun tidak dapat dibuktikan);
      semua scholar_id NULL; statistik `verifikasi_gagal`.
  P4. Nama profil tidak terbaca: semua baris 'belum_terverifikasi'
      (+statistik); jalur RAW tidak menggagalkan run untuk kondisi ini.

Aturan `author_role`: murni §3 (author_order==0 -> 'penulis_pertama', else
  'co_author') — berlaku di semua kondisi P1..P4 (role tidak menunggu
  verifikasi; mendukung K7: co_author + pemilik_profil serentak).

Penanganan kasus khusus (tugas #7):
  a. NAMA AMBIGU di Excel (NAMA sama, scholar_id beda): kunci masuk set
     ambigu -> verifikasi GAGAL -> P3 (belum_terverifikasi). Tanpa tebakan.
  b. scholar_id KOSONG di Excel (10 dari 139 baris nyata): baris itu tidak
     dipakai memverifikasi apa pun; bila tak ada kandidat lain -> P3.
     Dosa baca_dosen lama (run_batch mencatat DILEWATI tanpa menebak ID)
     dipertahankan.
  c. DAFTA TERPOTONG: string daftar memuat elipsis -> hanya nama sebelum
     elipsis yang jadi baris; elipsis tidak pernah jadi nama;
     daftar_terpotong=TRUE (D-1). Tidak ada nama yang diarang untuk
     melengkapi kehilangan.
  d. DETAIL GAGAL (429/blokir/timeout): pre-fill None + break sudah ada
     (scrape_scholar_playwright.py:913-976); fallback aturan sumber
     (detail-first publications.py:479-484 diterapkan di loader); 429 BUKAN
     alasan menghapus nama yang sudah ada (K12); tanpa retry agresif/rotasi/
     identitas baru.
  e. RETRY: ON CONFLICT (raw_publication_id, author_order) DO NOTHING +
     fallback SELECT raw_publication_id saat RETURNING kosong; transaksi
     atomik dengan envelope dipertahankan (postgres.py:2052-2091) -> retry
